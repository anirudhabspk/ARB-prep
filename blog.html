Progress toward recursive self-improvement depends on agents that can solve hard, open ended ML research problems quickly while producing solutions that generalize beyond the experiments they can see.

Open-ended ML research often takes many experiments. One-shot and few-shot evaluations [1] can miss the gains agents make over longer runs. PostTrainBench studies long-horizon agents, but focuses on LLM post-training [2]. An agent that starts behind may eventually outperform one that improves more slowly.

Vanilla auto-research evals [3] and other long-horizon benchmarks [4] also need to distinguish progress from overfitting. They reward improvements on feedback available during the run, without separately measuring whether those improvements generalize to held-out data. Long runs can therefore reward solutions that overfit the feedback.

To address these gaps, we introduce AutoResearchBench, a benchmark of open ended ML research tasks designed to measure how quickly agents improve over 24-hour AutoResearch runs while still generalizing to hidden test data.

We detail three contributions:

  • A benchmark for sustained ML research. AutoResearchBench spans 29 tasks and measures progress over 24 hours.
  • An evaluation that separates visible progress from generalization. Agents optimize validation scores, while hidden-test AUARC measures how quickly they find solutions that generalize.
  • An analysis of time, cost and agent behavior. Rankings change with the evaluation window, showing why a single time budget can miss differences between models. We also compare cost efficiency and how agents spend their research effort.

This section presents the headline results. We examine research strategies and model behavior in Analyzing agent behavior.

Experimental setup

We run AutoResearch with the standard Terminus 2 harness in a 24-hour benchmark window. Harnesses can significantly affect performance, so we compare all models using the same Terminus 2 harness to isolate model performance and evaluate them fairly. The harness itself lets each agent submit as many times as it wants. After every submission, the agent receives a validation score and its remaining time in the 24-hour window. It never sees hidden test scores. See the harness comparison for more information about the harness we used, and our comparison with Claude Code and Codex.

Evaluating agents over extended 24-hour runs lets us measure whether models sustain progress and whether repeated optimization of validation scores leads to overfitting, with gains that fail to generalize to hidden test data.

Each task uses the Harbor format, with separate work and verifier containers. To guard against reward hacking, our adversarial quality control and reward hacking agent inspects task environments and completed model rollouts. We have already used this agent to find issues in several widely used benchmarks and are working with the community to address them (blog coming soon). Models also have no internet access.

Effort levels for model evaluations

We ran each model at the highest effort level available, except Muse Spark. Its current highest effort level was not available when we generated its rollouts. Each model can produce at most 32,000 output tokens per turn.

Task scoring

Each task starts with its own "raw" score that the agent is tasked with optimizing, such as accuracy, speedup, or F1 score. We convert that raw score to a reward from 0 to 1 before returning the result to the agent. This gives results from different tasks a common scale.

When available, we use two guide "anchor scores" to perform the transformation to [0, 1]. These are the baseline and the reference solution. The baseline is the score of a simple method that the agent should beat. The reference is the score of a strong known method applied to the problem. If the agent submits the baseline, it usually receives a reward of 0. If it submits the reference, it receives a reward of 0.5.1 Results above the reference continue to earn more reward and approach the maximum score of 1.

1 Some tasks reserve rewards from 0 to 0.1 for results below the main baseline. Their reference receives 0.55.

Recall that the agent receives a validation reward after each submission. It never receives the hidden test reward. Most tasks use the same "anchor scores" to compute the resulting validation and hidden test scores.2 The agent can then get useful feedback without viewing the validation data directly.

2 A few use different guide points because their two data sets have different levels of difficulty. Describe why? This seems like a validation and test distribution mismatch.

Main evaluation metric: hidden-test AUARC

As an example, the charts below show Claude Fable 5.1 working on Faster language model generation on CPUs. The left curve plots the best submission up to time step t, as selected by the validation score. The right curve plots the test score of the submission with the best validation score so far. The agent never sees the hidden test scores or the curve on the right. The hidden test curve is not necessarily monotonic. If the agent is overfitting on the validation set, the hidden test score may drop relative to a prior submission.

Choosing the curve. At each point in time, the validation score selects the best submission so far. The hidden test curve shows the hidden test reward for that same submission. The hidden test result does not help select it.

Area under the curve. We calculate the area under the Auto Research Curve, or AUARC, across the run. This metric is equivalent to the time weighted average hidden test score. A score held for more time contributes more area. An improvement made early therefore adds more than the same improvement made near the end.

Combining tasks. Hidden test AUARC is our main measure of progress on one task. We compare models within each task, then combine those comparisons into a task relative Elo rating. This rating rises when a model has a higher hidden test AUARC than other models across tasks. We also report the final hidden test result so that a large improvement near the end remains visible.

For the common reporting scale, some raw measures have a clear best possible value. Accuracy has a best value of 100 percent. Error has a best value of zero. In these cases, we measure the distance from that best value.

Reward formula

Let d be the distance from the best possible result. We compare the agent's reduction in this distance with the reduction achieved by the reference.

u=max(0,log(dbaseline/dagent)log(dbaseline/dreference)) Reward=c+(1−c)u1+u

The logarithm measures proportional reductions in the distance. Each halving adds the same amount to u. Improving accuracy from 90 percent to 95 percent removes half of the remaining error. Improving from 98 percent to 99 percent also removes half of the remaining error.

The value u measures progress in units of the reference improvement. The baseline has u equal to 0. The reference has u equal to 1. The resulting reward is always between 0 and 1, and improvements beyond the reference still receive more reward.

The value c is the reward at the baseline. It is either 0 or 0.1. Results below the baseline receive no more than c. A perfect result receives 1.

Some tasks do not have a fixed best possible result. For these tasks, u is the improvement beyond the baseline divided by the improvement from the baseline to the reference. When a useful reference does not exist, we count reductions in the remaining error instead. The exact calculation is chosen to match meaningful progress on that task.

How well do agents' improvements generalize?

We compare validation and hidden-test AUARC. A smaller gap means closer agreement between the feedback agents optimize and their performance on unseen data.

How we measure the gap

At each point in a run, validation selects the best checkpoint so far. We evaluate that same checkpoint on hidden tests, which the agent never sees.

For each model, we average validation AUARC (V) and hidden-test AUARC (T) across its included tasks. The relative gap is (V − T) / max(|V|, |T|).

A larger positive gap means less of the validation performance carries over to hidden tests. Lines show 95% intervals from resampling tasks. The gap alone does not prove overfitting.

How much of agents' research is hyperparameter tuning?

We measure the share of rounds spent only on hyperparameter optimization (HPO), meaning parameter changes within an existing method.

In our sample, Anthropic's Fable and Opus spend fewer rounds doing only HPO than the other models. This points to a difference in research approach, though it does not establish that doing less HPO causes their stronger results.

We see only a weak association between submission count and test AUARC across models. We don’t see evidence that simply submitting more leads to higher scores on this benchmark. This suggests that naïve hill climbing through more submissions alone is insufficient, and that the quality of research steps matters.

Comparing harnesses

We compared Codex and Claude Code with Terminus 2 on five tasks, using the same models over 12 hours.

Average rewards differ across harnesses, but the aggregate hidden test ranking stays the same. Codex and Claude Code submit more than Terminus 2. Codex’s lower test AUARC is driven by Shortest CI, where validation improvements stopped transferring to the hidden test earlier than with Terminus 2.

These results support our choice to use Terminus 2 for all models. It provides a consistent setup and preserves the aggregate model ranking seen with native harnesses in this comparison.
